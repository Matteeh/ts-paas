## Context

Contract: every requirement in the `deployments` delta.

Create `src/deployments/reconcile.ts`. It takes `EngineDeps` from `src/deployments/types.ts`. Read state only through `listApps` in `src/state/apps.ts`, and `deploymentHistory`, `deploymentStatusChanges` and `setDeploymentStatus` in `src/state/deployments.ts`. Read the engine only through `listContainers({ [MANAGED_LABEL]: "true" })` and `inspectContainer`, plus `removeContainer(id, { force: true })` when pruning. `MANAGED_LABEL` comes from `src/runtime/types.ts` and `APP_LABEL` from `src/deployments/types.ts`. Treat `ContainerNotFoundError` on removal as removed. This module knows nothing about ingress; `paas-caddy` is excluded only because it has no `paas.app` label.

Match containers to deployments by container id. A deployment "stays" when it is `running` and not planned to fail, or in `pending`, `pulling` or `starting` and not stuck. The stuck check compares the time of the deployment's latest status change with `clock.now()`: more than `stuckAfterMs` before it is stuck, and exactly `stuckAfterMs` is not. The error for a stuck deployment is `stuck in <status> since <ISO time of that change>`.

Do not edit `src/deployments/engine.ts`, `stop.ts`, `types.ts` or any other file.

Tests use `FakeRuntime`, `FakeClock` and `openStore(":memory:")`, and seed deployments with `createApp`, `createDeployment` and `setDeploymentStatus`. For containers, create them through the fake with the labels the engine uses (`paas.app`, `paas.deployment`). Make one exit with a `FakeImageScript` exit code and delay, or with `stopContainer`, which gives code 0. Leave one in `created` by never starting it. To make a removal fail, subclass `FakeRuntime` in the test file and throw a `RuntimeError` from `removeContainer` for one name.

## Ports

```ts
// src/deployments/reconcile.ts
export const DEFAULT_STUCK_AFTER_MS = 600_000;
export type ReconcileItem =
  | { kind: "fail"; app: string; deploymentId: string; containerId: string | null; error: string }
  | { kind: "orphan"; app: string; containerId: string; name: string };
export interface ReconcileOutcome { item: ReconcileItem; result: "done" | "failed" | "reported"; error: string | null; }
export function planReconcile(deps: EngineDeps, options?: { stuckAfterMs?: number }): Promise<ReconcileItem[]>;
export function applyReconcile(deps: EngineDeps, plan: readonly ReconcileItem[], options: { prune: boolean }): Promise<ReconcileOutcome[]>;
```

## Acceptance
- [ ] A running deployment whose container runs, with no other app container, gives an empty plan, and `planReconcile` changes nothing in the store or the engine in every case below.
- [ ] A running deployment with no container, or with `containerId` `null`, is planned as `fail` with error `container disappeared`; one whose container exited with code 137 gets `container exited with code 137`; one in `created` gets `container is not running`.
- [ ] A deployment that entered `pulling` 10 minutes and 1 ms ago is planned as `fail` with `stuck in pulling since <that time>`; at exactly 10 minutes, or with `stuckAfterMs: 60_000` after 59 s, it is not planned.
- [ ] Containers with `paas.app` owned by no staying deployment are `orphan` items: a `replaced` deployment's leftover container, and the container of a deployment the same plan fails as exited. A container of a deployment in `starting` for one minute is not an orphan, and a container without `paas.app` (labels `paas.ingress=caddy`) never is.
- [ ] Items come out as failures ordered by app name, then orphans ordered by container name.
- [ ] `applyReconcile` without `prune` marks each failure `failed` with its error (outcome `done`), leaves orphans running (outcome `reported`); with `prune` it force-removes orphans (outcome `done`, and `done` too when the container is already gone).
- [ ] With `prune`, a removal that throws `RuntimeError("device busy")` gives outcome `failed` with error `device busy`, and the next orphan is still removed.
