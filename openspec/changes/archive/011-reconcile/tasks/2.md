## Context

Contract: "Reconcile command", "Reconcile output", "Reconcile JSON" and "Reconcile redeploy and ingress" in the `cli` delta.

Put the whole flow in an exported `runReconcile` in `src/commands/reconcile.ts`, and a `registerReconcile` that `buildProgram` in `src/program.ts` calls after `registerDoctor`. Change nothing else in `src/program.ts`. Task 3 calls `runReconcile` from `paas status`, so it must print nothing itself. The command runs inside `runAction` and `withEngine`, with `admin: getAdmin(context)` from `src/commands/context.ts`, and prints the report with `writeOutput` from `src/output.ts`. Exit 1 by throwing an `Error` whose message is `reconcile had <n> failed item(s)` when any item has `ok === false`. Print the report first, so stdout has every line and stderr gets `paas: reconcile had <n> failed item(s)`.

Flow in `runReconcile`:
- Call `planReconcile`, then `applyReconcile` (from `src/deployments/reconcile.ts`), unless `dryRun`.
- Build one report item per plan item. A `fail` stays kind `fail`, with the error as detail. An orphan is kind `prune` with `prune`, and kind `orphan` without it.
- With `redeploy`, add one `redeploy` item per app that was failed as disappeared or not running and has no running deployment left, calling `deploy` from `src/deployments/engine.ts` for each, in plan order. Stuck failures never cause a redeploy.
- Read `ingressStatus` from `src/ingress/caddy.ts`. When Caddy is `running`, and some item changed something (`fail`, `prune` or `redeploy`) or its routes differ as a set from `desiredRoutes(store)` in `src/ingress/config.ts`, add a `push-ingress` item and call `syncIngress`, unless `dryRun`. If reading Caddy's config fails, treat the routes as different. `<n> routes` counts `desiredRoutes` after the changes.

Details and `ok` follow the `cli` delta: `planned` and `ok: null` for every action a dry run skips, `ok: null` for a reported orphan, and `failed: <first line of message>` with `ok: false` for a failed action. Every item carries `app`, `deploymentId` and `containerId`, with `null` for what does not apply.

Tests follow `tests/ingress-deploy-cli.test.ts`: in-process `buildProgram(io, { env, runtime, clock, admin })` with one `FakeRuntime`, a `FakeClock` and a `FakeCaddyAdmin`. Copy its helpers; do not import from it. Deploy apps through the CLI, then create drift with `runtime.removeContainer(id, { force: true })` or `stopContainer`. Seed stuck deployments or leftover containers with `src/state` functions and the fake. A redeploy needs the clock advanced past the health window while the command runs. For "Caddy lost its routes", bring ingress up with `paas ingress up`, then call `admin.load(buildCaddyConfig("off", []))` directly, so that `getConfig` returns a config with no routes, as after a Caddy restart.

## Acceptance
- [ ] With every container in place, `paas reconcile` prints `nothing to reconcile` and exits 0; `paas --help` lists `reconcile` with a one-line description.
- [ ] After `web`'s container is removed by hand, `paas reconcile` prints `fail: web deployment <id> (container disappeared)`, exits 0, and the deployment is `failed`; `--dry-run --prune --redeploy` first prints `dry run: nothing was changed`, lists `fail` and `redeploy: web (planned)`, changes nothing, and exits 0.
- [ ] `--redeploy` after the container disappeared prints the `fail` line, then `redeploy: web (deployment <new id> is running)`, and `web` has a new running deployment; a deployment stuck in `pulling` gets a `fail` line and no `redeploy` line.
- [ ] A leftover container `web-old` prints `orphan: web-old (app web; use --prune to remove)` and stays; with `--prune` it prints `prune: web-old (removed)` and is gone; a removal failing with `device busy` prints `prune: web-old (failed: device busy)`, exits 1, and stderr is `paas: reconcile had 1 failed item(s)`.
- [ ] With ingress up and a running `web` (hostname `web.localhost`), after Caddy's config is replaced by one with no routes, `paas reconcile` prints `push-ingress: paas-caddy (1 routes)` and the admin's latest config routes `web.localhost`; when routes already match and nothing changed, there is no `push-ingress` item and no new load.
- [ ] After a disappeared container with ingress up, the `fail` item is followed by a `push-ingress` item, and the pushed config has no route for `web`.
- [ ] `--dry-run --json` prints one line `{"dryRun":true,"items":[...]}` whose `fail` item has `detail` `container disappeared` and `ok` `null`; without `--dry-run`, that item's `ok` is `true`.
