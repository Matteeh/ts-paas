## Context

Contract: "Failed start leaves no container" in the `ingress` delta.

In `createCaddy` in `src/ingress/caddy.ts`, wrap `startContainer` for the container it just created. On failure, `removeContainer(id, { force: true })`, ignore any error from that removal, and rethrow the original error unchanged. `ingressUp` then fails before it pushes anything. The "started" path, which starts an existing stopped `paas-caddy`, stays as it is: an existing container is left in place when its start fails. Change nothing else in the file. `tests/ingress-caddy.test.ts` is frozen and must pass unchanged, and the change-level `pnpm verify` runs it.

Tests use `FakeRuntime`, `FakeClock`, `FakeCaddyAdmin` and `openStore(":memory:")`, like `tests/ingress-caddy.test.ts`. Copy its helpers; do not import from it. Make a start fail by subclassing `FakeRuntime` in the test file: `startContainer` throws `new PortInUseError("rootlessport listen tcp 127.0.0.1:2019: bind: address already in use", "127.0.0.1:2019")` while a flag is set. `PortInUseError` comes from `src/runtime/errors.ts`. To make the removal fail too, throw from `removeContainer` in the same subclass.

## Acceptance
- [ ] When starting a newly created `paas-caddy` throws `PortInUseError`, `ingressUp` rejects with that same error object, no `paas-caddy` exists afterwards, and the admin received no config.
- [ ] When the removal also throws, `ingressUp` still rejects with the `PortInUseError`, not the removal's error.
- [ ] After a failed first up, clearing the flag and calling `ingressUp` again reports `created` and runs `paas-caddy`.
- [ ] When `paas-caddy` exists and has exited, and starting it fails, `ingressUp` rejects with the start's error and `paas-caddy` still exists.
- [ ] The same failure on the recreate path (a changed HTTP port) leaves no `paas-caddy`.
