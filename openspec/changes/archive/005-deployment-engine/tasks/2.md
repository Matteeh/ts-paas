## Context

`src/deployments/engine.ts` is the one module that owns the deploy flow. The flow is specified as scenarios in the `deployments` delta; follow them exactly.

Reuse, without editing:
- From `src/deployments/types.ts`: `EngineDeps`, `DeployEvent`, `containerName`, `PAAS_NETWORK`, `APP_LABEL`, `DEPLOYMENT_LABEL`, `DEFAULT_HEALTH_WINDOW_MS`, `DEFAULT_STOP_TIMEOUT_SECONDS`, `IN_PROGRESS_STATUSES`.
- `DeploymentInProgressError` from `src/deployments/errors.ts`.
- `checkHealth` and `healthFailureMessage` from `src/deployments/health.ts`.
- From `src/state/`: `getApp`, `updateApp`, `createApp`, `createDeployment`, `setDeploymentStatus`, `getDeployment`, `deploymentHistory`, `deploymentStatusChanges`, `openStore`.
- `ContainerNotFoundError` from `src/runtime/errors.ts`.
- `FakeRuntime` from `src/runtime/fake.ts` and `FakeClock` from `src/clock.ts`.

No SQL outside `src/state/`. No dependency changes; there is no network.

Flow:
1. `getApp`, then refuse if `deploymentHistory` has a deployment in `IN_PROGRESS_STATUSES`, then `createDeployment`, with no `await` between the check and the creation.
2. `pulling`, then `pullImage`.
3. `ensureNetwork(PAAS_NETWORK)`, then `createContainer` with the name, labels, network, `internalPort` (the app's port), `env` and `restartPolicy: "unless-stopped"`.
4. `starting` with the container id, then `startContainer`, then `checkHealth` with `options.healthWindowMs ?? DEFAULT_HEALTH_WINDOW_MS`.

When unhealthy: `removeContainer(id, { force: true })`, then `failed` with `healthFailureMessage`. When healthy: `running`, then for each other `running` deployment of the app, `stopContainer` with `options.stopTimeoutSeconds ?? DEFAULT_STOP_TIMEOUT_SECONDS`, then `removeContainer` with `force`. Treat `ContainerNotFoundError` as removed. Report any other error in the message, and mark that deployment `replaced` either way.

Any error thrown after `createDeployment` fails the deployment with that error's message, after a force-remove of the new container if one was created (ignore errors from that removal). Call `deps.onProgress` right after every `setDeploymentStatus` or `createDeployment`. Resolve with `getDeployment` of the new deployment.

Tests share one `FakeClock` across `openStore(":memory:", { clock, newId })` (a counter: `d1`, `d2`, ...), `FakeRuntime({ clock, scripts, pullFailures })` and `EngineDeps`. `FakeClock.advance` resolves only sleeps already registered: start `deploy` without awaiting, `await new Promise((resolve) => setImmediate(resolve))`, `await clock.advance(3000)`, then await the result. No test sleeps in real time. Switch the image between deploys with `updateApp`; fake scripts are per image. To see the created spec or inject a failure into one method, wrap the `FakeRuntime` in a test object implementing `ContainerRuntime` that delegates every other method.

## Acceptance
- [ ] First deploy of `web` (`nginx:1`, port 80, env `{A: "1"}`): status changes `pending`, `pulling`, `starting`, `running`; the resolved deployment is `running` with container id set; the created spec has name `web-d1`, labels `paas.app=web` and `paas.deployment=d1`, network `paas-net`, `internalPort` 80, env `{A: "1"}`, `restartPolicy` `unless-stopped`; the container is running with `paas.managed=true`.
- [ ] Redeploy: B is `running`, A is `replaced` with `finishedAt` set, and A's container is gone; `onProgress` receives, in order, B's `pending`, `pulling`, `starting`, `running`, then A's `replaced`, each with a non-empty message.
- [ ] Health failure: with A running, B's image scripted to write 25 log lines and exit with code 3 resolves `failed` with an error starting `container exited with code 3` followed by exactly the last 20 lines; B's container is gone; A stays `running` and its container runs.
- [ ] Pull failure: B's image in `pullFailures` resolves `failed` with the runtime's message, no container labelled `paas.deployment=<B id>` exists, and A stays `running`.
- [ ] Runtime errors: a pre-created container named `web-d2` makes B `failed` with the `NameConflictError` message; a wrapped `startContainer` that throws `RuntimeError("boom")` makes B `failed` with `boom` and removes B's container; in both, A stays `running`.
- [ ] A second `deploy` of `web` while the first waits in its health window rejects with `DeploymentInProgressError` and creates no deployment; `deploy` of an unknown app rejects with `AppNotFoundError`.
- [ ] Previous removal: a wrapped `removeContainer` that throws `RuntimeError("stuck")` for A's container leaves B `running` and A `replaced`, and A's `replaced` message contains `stuck`; if A's container was already removed out of band, A is `replaced` and the message does not report an error.
